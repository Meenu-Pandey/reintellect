# ReIntellect — Architecture and Design Choices

This document records the key technical decisions made during development of ReIntellect, the reasoning behind each choice, and the trade-offs considered.

---

## 1. Monolithic Backend vs Microservices

**Decision:** Single Python process containing DetectionPipeline, EventEngine, and FastAPI.

**Reasoning:**
- Communication between pipeline, engine, and API via `asyncio.Queue` eliminates network serialisation and latency
- Deployment is a single Docker image — no service discovery, no inter-service auth
- SQLite as the persistence layer is sufficient at hackathon scale and avoids a separate database container
- The total pipeline latency budget (camera frame → WebSocket push ≤ 500ms) is achievable without inter-process hops

**Trade-off:** Horizontal scaling requires breaking the monolith. Acceptable for a single-store hackathon deployment; a production system would split detection, engine, and API into separate services communicating via a message broker (e.g., Kafka or Redis Streams).

---

## 2. YOLOv8n for Person Detection

**Decision:** YOLOv8n (nano variant) with confidence threshold 0.5 and minimum bounding box height 50px.

**Reasoning:**
- YOLOv8n achieves 10+ FPS on CPU (Intel Core i5 class), satisfying the minimum system requirement without mandatory GPU
- The nano variant sacrifices ~5% mAP versus YOLOv8s in exchange for 3× inference speedup — an acceptable trade at retail store density (typically <20 persons in frame)
- Confidence threshold 0.5 eliminates most false positives from reflections, mannequins, and partial detections
- Minimum bbox height 50px filters out distant detections that would generate spurious tracks

**Trade-off:** A larger model (YOLOv8m or YOLOv8l) would improve detection of partially occluded persons and persons at the edge of frame. This is the primary accuracy lever available with GPU deployment.

---

## 3. ByteTrack for Multi-Object Tracking

**Decision:** ByteTrack with a 30-frame re-association window.

**Reasoning:**
- ByteTrack handles full occlusions better than SORT by tracking low-confidence detections, reducing identity switches in crowded retail environments
- The 30-frame window (≈1s at 30 FPS) handles typical occlusion durations (person behind shelf, partial exit)
- ByteTrack is integrated directly into the Ultralytics library, avoiding an additional dependency

**Trade-off:** ByteTrack does not use appearance features (ReID). A person who walks behind a large display for >30 frames receives a new `track_id`. The `VisitorRegistry.merge_camera_handoff()` method partially compensates for this at camera boundaries (≤10s gap), but does not solve mid-zone identity loss.

---

## 4. Staff Classification via HSV Colour Heuristic

**Decision:** Staff filter based on HSV colour range of staff uniform, with configurable threshold.

**Reasoning:**
- No labelled training data for Purplle staff uniforms was available to fine-tune a classifier
- The HSV heuristic is fast (single ROI crop + `cv2.inRange`) and adds near-zero latency to the pipeline
- Configurable HSV bounds and proportion threshold allow adaptation to different store uniform colours without retraining

**Trade-off:** Colour-based classification fails when a customer wears similar colours to staff. A production system would use a fine-tuned uniform classifier or badge detection model. The current implementation is a pragmatic placeholder that correctly handles clearly distinctive uniforms.

---

## 5. SQLite with WAL Mode vs PostgreSQL

**Decision:** SQLite with WAL (Write-Ahead Logging) mode enabled via `PRAGMA journal_mode=WAL`.

**Reasoning:**
- SQLite requires zero setup (no separate container, no connection pooling daemon)
- WAL mode allows concurrent reads during writes — the `event_consumer` task writes while REST endpoints read without blocking
- `aiosqlite` provides a non-blocking async wrapper that integrates cleanly with FastAPI's async event loop
- At hackathon scale (single store, <500 events/minute), SQLite comfortably handles the write throughput

**Trade-off:** SQLite does not support multi-process concurrent writes. Horizontal scaling the backend would require migrating to PostgreSQL. The `Database` class interface is intentionally abstracted (connect/execute/fetchall/fetchone) to make this migration low-risk.

---

## 6. Client-Supplied `event_id` for Idempotency

**Decision:** `event_id` is a UUID v4 supplied by the detection pipeline, not generated by the server.

**Reasoning:**
- The pipeline can retry failed ingestion calls with the same `event_id` and `INSERT OR IGNORE` guarantees exactly-once persistence
- Server-generated IDs would require the client to inspect the response to learn the assigned ID, complicating retry logic
- UUID v4 provides sufficient collision resistance for the expected event volume

**Trade-off:** Clients must generate UUIDs before calling `POST /events/ingest`. This is straightforward in Python (`uuid.uuid4()`) and imposes no meaningful burden.

---

## 7. `visitor_id` vs `track_id` Separation

**Decision:** `track_id` (ByteTrack internal) is never exposed in the public API. `visitor_id` (UUID v4) is the stable public identifier.

**Reasoning:**
- `track_id` is an ephemeral integer that changes on every new track assignment, including after re-association gaps ≥30 frames
- Exposing `track_id` in the event stream would break downstream consumers every time a track is reassigned
- `visitor_id` is assigned once at `ENTRY` confirmation and persists across camera handoffs and re-entries within 300s

---

## 8. Shapely for Zone Containment

**Decision:** `shapely.geometry.Point.within(Polygon)` for zone boundary tests.

**Reasoning:**
- Shapely provides numerically robust polygon containment that handles edge cases (centroid exactly on boundary, non-convex zones)
- The library is already a dependency of many geospatial stacks and adds minimal overhead
- Zone polygons are typically simple quadrilaterals — Shapely's point-in-polygon test is O(n) with n = polygon vertices, effectively O(1) for 4-vertex zones

**Trade-off:** Shapely adds ~10ms to initial import time. Negligible compared to YOLOv8 model loading.

---

## 9. WebSocket Connection Manager (In-Memory Registry)

**Decision:** `ConnectionManager` maintains a `dict[store_id, set[WebSocket]]` in process memory.

**Reasoning:**
- No external pub/sub (Redis, Kafka) required — all connections are within the same process
- Broadcast to all store connections is a simple async for-loop; at ≤50 connections per store, this completes well within the 200ms budget
- Failed connections are closed with code 1011 and removed without affecting others

**Trade-off:** Connections are not persistent across backend restarts. Clients reconnect automatically via the Zustand store's exponential backoff. In a multi-process deployment, an external broker would be required.

---

## 10. React Query + Zustand for Frontend State

**Decision:** TanStack React Query for REST polling; Zustand for WebSocket-driven live state.

**Reasoning:**
- React Query handles caching, stale-time, refetch intervals, loading/error states, and request deduplication — eliminating boilerplate for 5 REST endpoints
- Zustand provides a minimal, non-opinionated store for the WebSocket state machine (visitor count, queue depth, last 20 events, connection status) without Redux ceremony
- The separation is clean: REST data (historical aggregates) → React Query; live data (WebSocket events) → Zustand

---

## 11. Vite Proxy Rewrite for `/api`

**Decision:** Vite dev server rewrites `/api/*` → `/*` before forwarding to the backend.

**Reasoning:**
- The backend registers routes at root (`/stores`, `/health`, etc.) without an `/api` prefix
- The Vite proxy `rewrite: (path) => path.replace(/^\/api/, "")` strips the prefix before forwarding
- Nginx in production does the same: `proxy_pass http://backend:8000/;` under `location /api/`
- This keeps the backend routes clean and avoids a naming collision with the frontend's own routes

---

## 12. Framer Motion for Dashboard Animations

**Decision:** Framer Motion for all dashboard and landing page animations.

**Reasoning:**
- Framer Motion's declarative API (`initial`, `animate`, `whileHover`, `useInView`) integrates cleanly with React's component model
- `AnimatePresence` handles mount/unmount transitions for the Live Feed event list without manual ref management
- `useInView` triggers scroll-based section reveals on the landing page without a separate Intersection Observer implementation

**Trade-off:** Adds ~35 KB gzip to the bundle. Acceptable given the visual quality improvement.

---

## 13. Demo Data Seeder

**Decision:** `python -m db.seed_demo_data` populates one full operating day of realistic Brigade Road store activity.

**Reasoning:**
- Real CCTV footage takes 10–30 minutes to accumulate meaningful analytics
- The seeder produces 206 visitors, 1,300+ events (all 8 types), 3,300 track positions, 60 POS transactions, and 5 anomalies — enough to populate all dashboard screens immediately
- Hourly distribution follows a realistic retail pattern (peak at 1 PM and 5–7 PM)
- All visitor IDs, event IDs, and timestamps are UUID v4 / ISO 8601 — fully compatible with the `POST /events/ingest` schema

---

## 14. Zone Polygon Coordinate System

**Decision:** All zone polygons use normalised coordinates [0.0, 1.0] relative to the camera frame dimensions.

**Reasoning:**
- Normalised coordinates are resolution-independent — the same polygon definition works for 720p, 1080p, and 4K feeds
- The `Shapely.Point.within(Polygon)` test operates on the same normalised coordinate space as the YOLOv8 bbox output (also normalised by the pipeline)
- The heatmap grid cells also use [0.0, 1.0] — all spatial data is directly comparable
